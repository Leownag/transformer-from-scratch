**兩個發現**

1. **PPL 對模型大小嚴格單調遞增** —— 最小的模型贏,每次加寬都更差。因為 1e15 是嚴重
   **data-limited** 的預算:s1 跑 1352 步看過 22.2M token,s4 只有 414 步、6.8M token,
   少了 3.3 倍。五個模型都還在 loss 曲線的陡降段,此時多一步遠比多一個參數值得。
2. **學習率有幫助但影響小一個量級** —— 同架構下 `max_lr` 從 1e-3 提到 3e-3,PPL 從
   517.77 改善到 477.27(40 點);但模型大小造成的差距是 371 點。

**合規驗證**：五組 `train FLOPs` 都是 1.00e15 或以下(`train.py` 自行印出),無超預算警告;
模型大小 29.1–94.3 MB,無 100MB 警告;`MaxRSS 12.3 GB` 在 12 GiB 限制內(97.8%)。

## 2. 為什麼 `n_embd` 上限是 320

因為有 weight tying,參數量主要是 token embedding `50257 × n_embd`:

| n_embd | 檔案大小 | 可用? |
|---|---|---|
| 256 | 70.7 MB | ✅ |
| 320 | 94.3 MB | ✅ 上限 |
| 384 | ~120 MB | ❌ 超過 Gradescope 100MB |

PDF 沒提這件事,但 Q3.5 要交 `model.pt`,選了 384 就交不出去。

## 3. ✅ Q3.5 的策略張力 —— 已用實驗解決

**結論：交叉驗證證實 Q3.4 的 1e15 排名無法外推到 1e17。**

| 預算 | e128/h4/l4 | e256/h8/l6 |
|---|---|---|
| 1e15 | **306.04** ← Q3.4 贏家 | 517.77 |
| 1e16 | 73.89 | **60.67** ← 排名反轉 |
| 1e17 | 59.85（半分區間） | **38.34** ✅（滿分區間） |

三個預算都實測，不是外推。e256 在 1e15 落後 69%，1e16 反超 18%，1e17 領先 36%。
**若照 Q3.4 的字面答案選 e128，最終只能拿半分** —— 那 1.3 小時的 1e16 階梯實驗價值 10 分。

最終交件：`q35-e256`，val PPL **38.34**，model.pt 70.7 MB，train FLOPs 1.00e+17。

## 3b. （原始分析，保留備查）⚠️ Q3.5 的策略張力

Q3.4 的贏家是**最小**的 `s1-e128`,但 Q3.5 預算放大 100 倍到 1e17,而規則不准改
model hyperparameters。問題是:

- `s1-e128` 的 7.3M 參數裡,token embedding 佔 `50257×128 = 6.43M`,
  **真正的 transformer 參數只有約 0.87M**。
- 在 1e17 下它能跑 135,252 步 = 2216M token = **4.3 個 epoch**。
- 以 scaling law 的經驗,compute-optimal 模型大小大致隨預算開根號成長;
  預算 ×100 意味著最佳參數量約 ×10,指向 e320–e384 區間,**不是 e128**。

換言之 **1e15 的排名不是 1e17 的可靠預測器**。照 Q3.4 結果選 e128 是忠於題目要求
(「find the best configuration when training with at most 1e+15 FLOPs」),
但它在 1e17 下可能因容量不足先飽和,而 Q3.5 的計分門檻是 PPL < 50 滿分、< 75 半分。

**建議的下一步**:花約 20 分鐘做一個 **1e16 的交叉驗證**(預算 ×10,各組約 10 分鐘),
看排名是否在中間預算就反轉。只要測 `s1-e128` 與 `s3-e256` 兩組就能看出趨勢:

- 若 e128 仍領先 → 放心用 e128 跑 Q3.5
- 若排名反轉 → 說明交叉點在 1e15 與 1e16 之間,Q3.5 該用較大的架構,
  並在報告中誠實說明「以 1e15 選出的最佳組態不是 1e17 的最佳組態」

這個實驗很便宜,但能避免把 20 分的 Q3.5 押在一個外推假設上。

## 4. Q3.5 的兩個技術障礙

1. **`train.py` 沒有 checkpoint/resume** —— `model.pt` 只在訓練全部跑完才存
   (`train.py:321`)。`courses-gpu` 簡報所述上限 8 小時(線上 `MaxTime` 為 24 小時),
   一旦撞到 wall clock 就全部白跑。課程簡報第 31 頁明確建議
   「Checkpoint and resume across several shorter jobs」。**Q3.5 之前應該補上週期性存檔。**
2. **記憶體已經很緊** —— 本次 `MaxRSS` 達 12.3 GB,是 12 GiB 限制的 97.8%。
   主因是 `train.py:265` 把 520M 個 `uint16` token 用 `.astype(int)` 轉成 int64 = 4.16 GB。
   Q3.5 跑更久、步數更多,建議提高 `--mem`(線上 `MaxMemPerNode` 其實是 UNLIMITED)。

時間估算(V100,實測 5.5 TFLOPS;Volta 不支援 bf16 所以是 fp32):
1e17 FLOPs ÷ 5.5e12 ≈ **5.1 小時**。超過簡報的 8 小時上限不多,但沒有 resume 就很危險。

| # | 問題 | 原因 | 修正 |

| 5 | **conda 死鎖** | 兩個 `conda create` 都停在 `futex_wait_queue`,套件已解開 4316 檔但 env 目錄沒建立。VAST 網路檔案系統上 flock 異常,multiprocessing 平行解壓永久等待。**兩次重現** | 改用 `python -m venv`(5 秒完成) |

| 8 | **預設 torch 在 V100 上會失敗** | 預設 PyPI 現在給 torch 2.14.1+**cu130**,而 CUDA 13 移除了 Pascal(sm_60)與 Volta(sm_70)支援 —— 正好是 `courses-gpu` 的全部硬體 | 釘住 `--index-url .../whl/cu121` |

**第 7 項的代價**:`/tmp` 是節點本機,所以 env 無法跨 job 重用,每個 job 要重建約 4 分鐘。
判斷是值得的 —— wheel 已快取在 `$CW/pip_cache`,不需重新下載。

**實測的檔案系統特性**(反直覺,值得記錄):

| 操作 | /tmp | /scratch | /courses |
|---|---|---|---|
| 建 500 個小檔 | 0s | 2s | 3s |
| 循序寫 512MB | 8s | — | **4s** |

`/courses` 處理大檔比本機還快(128 MB/s),問題只出在「大量小檔 + cgroup 記憶體壓力」。
所以 544MB 的 `tokens.npz` 下載到 `/courses` 只花 37 秒。

## 6. 校園計算資源使用規範遵守情況

| 規定 | 遵守方式 |
|---|---|
| 不在 login node 運算 | 所有運算都在 compute node(`c0584`/`c3014`/`d1004`);login node 只做檔案複製與 `sbatch` 提交 |
| Keep /home small | **home 最終 18K**。過程中 conda 曾誤寫 274M 進去,已清除並改導向課程空間 |
| env/快取放課程空間 | `pip_cache`、`hf_cache`、`wandb`、`outputs`、`tokens.npz` 全在 `/courses/<course>/students/$USER`(共 5.4G) |
| 用 courses / courses-gpu | sweep 用 `courses-gpu`;環境建置與資料下載用 `courses`(CPU),不浪費 GPU |
| 一次一個 GPU job | 五組**循序跑在單一 job** 內,`--gres=gpu:1`,全程未同時佔用多個 GPU slot |
| Right-size the request | `--mem=12G`(簡報上限)、`--time=04:00:00`(預設值),實際只用 31 分鐘 |
| 不要閒置佔用 GPU | 用 `sbatch` 而非互動式 session;job 跑完即釋放,佇列已確認為空 |
| 載入 explorer module | 每個 job 都 `module purge` 後 `module load explorer anaconda3/2024.06 cuda/12.1.1` |
| 不留垃圾在共用節點 | `/tmp` 的 venv 有 `trap cleanup EXIT`,job 結束自動刪除 |
